# Root cause analysis — two major defects

Method: **5 Whys** (each answer verified in the source or by a test, not guessed) + **fishbone** (Ishikawa) with the categories *Requirements/Docs, Design, Code, Process/Review, Tools/Tests, Environment*. Figures: `docs/figures/fishbone_F13.png`, `docs/figures/fishbone_F3.png` (generated by `scripts/team/fishbone.py`).

## RCA-1 — F13 (#1): issuing the pre-filled quantity deducts no stock
**Symptom:** the Admin issues a requisition with the quantities the screen suggests; the requisition shows *Issued* and the success message appears, but stock is unchanged and no outward transaction exists. Severity S1 — the inventory silently drifts from reality on the *normal* path of WF2.

### 5 Whys
| # | Why? | Answer (evidence) |
|---|---|---|
| 1 | Why is stock not reduced? | `IssueItemsView.form_valid` only posts a transaction and decrements stock for lines with `quantity_issued > 0`; after `formset.save()` the line still has `quantity_issued = 0` (UT63, API X4). |
| 2 | Why is `quantity_issued` still 0 after saving? | `formset.save()` did not save that line at all. |
| 3 | Why did the formset skip the line? | Django's `BaseModelFormSet.save_existing_objects()` skips every form whose `has_changed()` is False. |
| 4 | Why does the form report "not changed" when the user submitted 4? | `RequisitionLineItemUpdateForm.__init__` puts the requested quantity (4) into `self.initial`. The submitted value equals the initial value, and the notes field is empty as initially, so Django concludes nothing changed. |
| 5 | Why was this not noticed? | The UI pre-fill (FR-08) was implemented as an *initial* value instead of setting the instance field; there were no automated tests, and a manual check usually changes a number (which works). The success message is shown regardless of what was saved. |

**Root cause:** a presentation default (pre-filled value) was implemented through Django's change-detection mechanism, which the save logic then depends on; no test covered the "accept the defaults" path.

### Fishbone (summary)
* **Requirements/Docs:** README says issuing "automatically deducts quantities" but does not say the default must be issuable unchanged; no acceptance criterion for the default path.
* **Design:** stock posting depends on what the formset chose to save instead of on the submitted quantities; the success message is not derived from the outcome.
* **Code:** `self.initial[...] = quantity_requested` in `__init__`; `formset.save()` + reading back the DB.
* **Process/Review:** no review evidence in the upstream history (2 commits); no definition of done.
* **Tools/Tests:** upstream has no tests; manual testing tends to edit the number.
* **Environment:** none.

### Corrective action
Save every line form explicitly (not only changed ones) before posting stock, so the submitted quantity is always persisted — fix PR (fails before / passes after): UT63, API X4, UC-03 main/A1 turn from expected-fail to pass; markers removed.

### Preventive actions
1. Keep the "accept the defaults" tests (UT63, X4, UC-03 main) in the CI gate.
2. Assert the *outcome* in every write test (stock + transaction), never only the message — rule added to the test plan.
3. Mutation operator `StockDeltaOffByOne` and stock read-back assertions stay in the mutation gate.

## RCA-2 — F3 (#2): any logged-in user can issue items
**Symptom:** an HOD (or initiator) opens `/requisition/<pk>/issue/` and completes the issue; stock moves, `issuer` = the HOD. Severity S1 — breaks separation of duties.

### 5 Whys
| # | Why? | Answer (evidence) |
|---|---|---|
| 1 | Why can an HOD complete an issue? | `IssueItemsView` returns the page and accepts the POST for any authenticated user (SEC-03, SEC-08, DT-4). |
| 2 | Why is there no role check? | The view only inherits `RequisitionMixin(LoginRequiredMixin)`; login is checked, role is not. |
| 3 | Why was the role check left out? | An `AdminRequiredMixin` exists in the same file (`views.py:76`) but no view uses it (UT130 shows the mixin works) — the authorisation design was written and never wired in. |
| 4 | Why did nobody see that? | The UI hides the *Issue* button from non-Admins (`requisition_detail.html` checks `is_admin`), so in normal clicking the page is never reached — security by hidden link. |
| 5 | Why was hiding the link considered enough? | No access-control requirement or test existed; authorisation was treated as a UI concern instead of a server-side rule. |

**Root cause:** authorisation implemented in templates (button visibility) instead of on the server; the server-side mixins were created but never applied, and nothing verified the server-side decision.

### Fishbone (summary)
* **Requirements/Docs:** README describes roles in prose; no explicit access matrix.
* **Design:** authorisation spread between templates and querysets; no single policy point.
* **Code:** `AdminRequiredMixin`, `HODRequiredMixin`, `InitiatorRequiredMixin` defined but unused; `HODApprovalView` grants Admins full access (related F4).
* **Process/Review:** no security review.
* **Tools/Tests:** no access tests; SonarQube cannot know business roles (no issue raised).
* **Environment:** DEBUG on, so 403/404 behaviour was never exercised like production.

### Corrective action
Add `UserPassesTestMixin`-based Admin check to `IssueItemsView` (fix PR; SEC-03/06/08, UT69, API DT-4 and M8 flip from expected-fail to pass). Same pattern for F4 in `HODApprovalView`.

### Preventive actions
1. The Playwright access matrix (SEC-01..08) and API DT-1/DT-4 run in CI on every PR.
2. Rule: every state-changing view must declare its role check on the server; the custom mutation operator `DropConjunct` keeps testing every authority condition.
3. Access matrix kept in the test basis as the specification of permissions.
